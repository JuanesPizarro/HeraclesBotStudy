# Mobile API V1 Contract

This document defines the first mobile-facing API surface for Heracles.

The goal is not to replace the current web app endpoints immediately. The goal
is to introduce stable, versioned contracts that an Expo/React Native client can
consume without depending on Telegram-specific flows or Alpine.js payloads.

## Scope

V1 covers the core training loop:

1. Authenticate the user with the current transitional token mechanism.
2. Read the current profile and active routine summary.
3. Read today's session plan.
4. Log completed sets.
5. Read today's logged sets.
6. Finish/evaluate a session idempotently.
7. Send a message to the coaching agent.

Out of scope for V1:

- New-user onboarding UI.
- Native push notifications.
- Social features.
- Payments.
- Replacing Telegram identity as the source of existing accounts.

## Authentication

Initial mobile V1 uses the same `web_token` already generated by `/webapp`.

Request format:

```http
Authorization: Bearer <web_token>
```

This is transitional. Before public/mobile release, decide the long-term mobile
authentication provider and map it to `users.id` through `external_identities`.

Rules:

- Never expose `telegram_id` to the client as an editable field.
- Never accept `user_id` in request bodies.
- All writes derive the user from the bearer token.
- Return `401` for missing/invalid credentials.

## Versioning

All mobile endpoints should live under:

```text
/api/v1
```

The existing `/api/session/*`, `/api/routines/*` and `/api/agent/message`
endpoints remain as web/legacy endpoints until the mobile client is stable.

V1 responses should prefer explicit response models over ad hoc dictionaries.
When a breaking response change is needed, add `/api/v2` instead of silently
changing V1.

## Endpoints

### GET `/api/v1/me`

Returns the authenticated user's profile and high-level training setup.

Response:

```json
{
  "id": "internal-user-uuid",
  "name": "Juan",
  "goal": "ganar fuerza y masa muscular",
  "training_days": ["domingo", "lunes", "miércoles", "jueves", "viernes"],
  "session_minutes": 60,
  "equipment": "home",
  "experience_level": "intermediate"
}
```

Implementation source:

- `UserStore.get_user_by_token`
- existing `/api/session/me` logic for compatibility

### GET `/api/v1/session/plan`

Returns the screen-oriented plan for the current local date in
`settings.TIMEZONE`.

Response for a training day:

```json
{
  "date": "2026-07-19",
  "today_day": "domingo",
  "is_rest_day": false,
  "day_name": "DÍA 1 — UPPER (Domingo)",
  "session_id": "1129119572:2026-07-19:24",
  "override": {
    "target_date": "2026-07-19",
    "scope": "day",
    "reason": "modificación temporal solicitada"
  },
  "exercises": [
    {
      "name": "Press militar con mancuernas (agarre neutro)",
      "target_sets": 3,
      "target_reps": "8-10",
      "suggested_weight": 10,
      "suggested_rest": 120,
      "note": "RIR 2-1-1",
      "is_circuit": false
    }
  ]
}
```

Response for a rest day:

```json
{
  "date": "2026-07-20",
  "today_day": "lunes",
  "is_rest_day": true,
  "next_training_day": "miércoles",
  "exercises": []
}
```

Rules:

- Exercise names must be canonical. See `docs/EXERCISE_IDENTITY.md`.
- If a session override exists for today and contains parseable bullets, it
  replaces the base routine plan for that date.
- Include `session_id` so mobile can finish the exact session it logged.

Implementation source:

- `_build_session_plan_payload`
- `UserStore.get_or_create_training_session`

### GET `/api/v1/session/today`

Returns sets logged for the current local date.

Response:

```json
{
  "date": "2026-07-19",
  "sets": [
    {
      "id": 123,
      "session_id": "1129119572:2026-07-19:24",
      "exercise": "Press militar con mancuernas (agarre neutro)",
      "set_number": 1,
      "reps": 10,
      "weight_kg": 10,
      "rpe": 8,
      "notes": ""
    }
  ]
}
```

Implementation source:

- `UserStore.get_today_workouts`

### POST `/api/v1/session/sets`

Logs one completed set.

Request:

```json
{
  "session_id": "1129119572:2026-07-19:24",
  "exercise": "Press militar con mancuernas (agarre neutro)",
  "reps": 10,
  "weight_kg": 10,
  "rpe": 8,
  "notes": ""
}
```

Response:

```json
{
  "id": 123,
  "session_id": "1129119572:2026-07-19:24",
  "exercise": "Press militar con mancuernas (agarre neutro)",
  "sets": 1,
  "reps": 10,
  "weight_kg": 10,
  "rpe": 8,
  "notes": ""
}
```

Validation rules:

- `session_id` must belong to the authenticated user.
- `exercise` must match a canonical exercise in today's plan unless explicitly
  supported as a manual extra exercise.
- `reps >= 1`.
- `weight_kg >= 0`.
- `rpe` is optional; when present it must be between 6 and 10.

Implementation source:

- existing `/api/session/set`
- `UserStore.save_workout`

### POST `/api/v1/sessions/{session_id}/finish`

Finishes and evaluates a session. This must be idempotent.

Headers:

```http
Idempotency-Key: <client-generated-key>
```

Response:

```json
{
  "session_id": "1129119572:2026-07-19:24",
  "evaluation": "Buen cierre de sesión...",
  "suggestions": [
    {
      "exercise": "Press militar con mancuernas (agarre neutro)",
      "next_weight": 10,
      "next_sets": 3,
      "next_reps": "8-10",
      "reason": "consolidate",
      "basis": "RPE alto"
    }
  ],
  "idempotent": false
}
```

Rules:

- Repeated calls for an evaluated session return cached `evaluation_json`.
- In-progress duplicate calls return `409`.
- Agent output is always validated before persistence.
- Fallback deterministic progression must keep the endpoint usable when the LLM
  fails.

Implementation source:

- existing `/api/sessions/{session_id}/finish`
- `_finish_training_session`

### POST `/api/v1/agent/messages`

Sends a user message to the coaching agent.

Request:

```json
{
  "message": "¿Qué me toca hoy?"
}
```

Response:

```json
{
  "message": "SÍ — Domingo es día de entrenamiento...",
  "actions": [],
  "requires_confirmation": false
}
```

Rules:

- Channel should be stored as `mobile`.
- Response uses `AgentResponse`.
- Tool permissions still derive from classified intent and trusted runtime
  context.

Implementation source:

- existing `/api/agent/message`
- `run_agent_message`

## Implementation Order

Implemented:

- `bot/handlers/mobile_api.py` with `APIRouter(prefix="/api/v1")`.
- `/api/v1/me`.
- `/api/v1/session/plan`.
- `/api/v1/session/today`.
- `/api/v1/session/sets`.
- `/api/v1/sessions/{session_id}/finish`.
- `/api/v1/agent/messages`.
- Tests for bearer auth, profile, plan, set logging and canonical exercise
  validation.

Remaining implementation work:

1. Move shared auth helpers toward `bot/api/dependencies.py` or reuse current
   helpers first if keeping the patch small.
2. Add fuller Pydantic response models for V1 payloads.
3. Add HTTP-level integration tests once the test client hang is understood.
4. Add idempotent finish tests through the mobile wrapper.
5. Keep the existing web app endpoints unchanged until the mobile client is
   migrated.

## Expo Client Screens

The first Expo app should be a training tool, not a marketing screen:

- Today: plan, exercise list, current set input, rest timer.
- Session log: completed sets grouped by exercise.
- Finish: evaluation and next targets.
- Coach: compact chat view using `/api/v1/agent/messages`.
- Profile: read-only basics plus app token/session state.

Onboarding can remain Telegram-only until authentication and account creation
are redesigned.
