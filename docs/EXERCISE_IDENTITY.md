# Exercise Identity And Persistence

Heracles must treat exercise names as stable domain identifiers, not as free
copy generated by the model.

The current SQLite schema stores exercise-level data in multiple places:

- `routines.routine_text` / `routines.routine_json`: prescribed exercise names.
- `workouts.exercise`: completed exercise names logged by the user.
- `progression_targets.exercise`: next prescription per exercise.
- `session_overrides.modification`: temporary day plans parsed by the web app.

Because `progression_targets` uses `(user_id, exercise)` as its primary key,
small spelling changes create different logical exercises. For example,
`Remo a una mano con mancuerna`, `Remo mancuerna unilateral` and `Remo con
mancuerna a 1 brazo` would not share progression history unless normalized.

## Canonical Name Rule

For every exercise already known to the user, the backend and the agent must
reuse the same canonical name when the exercise is semantically the same.

Canonical source priority:

1. Active structured routine exercise name, when `routine_json` exists.
2. Active routine text bullet name, when using legacy text routines.
3. Active session override bullet name, for temporary substitutions.
4. Existing `progression_targets.exercise`, when matching previous history.
5. Existing `workouts.exercise`, only as fallback for legacy/manual entries.

If the agent wants to refer to a known exercise, it must use the exact canonical
name from the context. It may explain variants in prose, but persisted fields
and web-app plan bullets must keep the canonical name.

Examples:

- Same exercise, same key: `Press militar con mancuernas (agarre neutro)`.
- Temporary substitution, new key for that day: `Remo a una mano con mancuerna`.
- Do not alternate between `Fondos en banco`, `Fondos en silla` and
  `Fondos en banco/silla` after one canonical name has been chosen.

## Agent Validation Requirement

Before presenting or persisting a plan, the agent should validate every exercise
against the known exercise catalog in context:

- If it is the same movement as an existing exercise, reuse the existing name.
- If it is a deliberate substitution, create one clear new canonical name and
  use that exact name in the whole response and any tool payload.
- If the substitution is temporary, store it in `session_overrides`, not in the
  active base routine.
- If the exercise has a known progression target, preserve that key so the web
  app can pre-load the correct weight/reps/sets.

The backend should enforce this in code over time with a resolver such as:

```text
resolve_exercise_name(user_id, proposed_name, allowed_context)
```

The resolver should return either:

- the canonical known exercise name,
- a new approved substitution name, or
- a validation error when the model invented or renamed an exercise without a
  clear reason.

## Web App Parsing Contract

Temporary overrides are parsed by the web app only when `modification` includes
routine-style bullets:

```text
• Exercise name: 3x10-12 @ 7 kg — note
```

For consistent persistence:

- Put the canonical exercise name before the colon.
- Use that same name when saving completed sets.
- Store or update `progression_targets` using that exact name.
- Keep aliases only in notes after the prescription, not in the key.

This is why a manual override that introduces `Remo a una mano con mancuerna`
should also persist a matching `progression_targets.exercise` row if the web app
must pre-load a weight for it.

## Future Schema Direction

The long-term fix is a dedicated exercise catalog:

- `exercises(id, canonical_name, aliases, movement_pattern, equipment)`
- `user_exercises(user_id, exercise_id, display_name, status)`
- routine, workout and progression tables referencing `exercise_id`

Until that exists, exact exercise-name strings are the compatibility layer.
Treat them with the same care as database IDs.
